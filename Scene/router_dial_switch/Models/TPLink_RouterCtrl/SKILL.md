## 第一部分 · 任务表(适配人员填这里)

这台机没有网页界面 —— 下面写的是"交给内部库什么、指望它回什么",
不是点哪个按钮。

```yaml
设备:
  品牌: TPLink
  型号: RouterCtrl
  怎么连: 不开浏览器 —— 这是自家样机,用内部库 RouterCtrl 下发
  地址和密码: 见 config.yaml 的 router.ip / router.pass

任务:
  名字: dial_switch
  说明: 把 WAN 口的拨号方式切成指定的那一档,填好那一档要的账密,保存

# ============ 第一段 · 前置(每次开工都要先走一遍的路)============
前置:
  - 怎么做: 不用点任何界面。把档名交给内部库,它自己下发并回读
    做完的样子: 拿回一份结果,里面写着「现在是哪一档」和「拨上了没有」

# ============ 第二段 · 状态表(一档一段)============
状态表:
  - 状态名: dynamic
    下拉里选哪一项(界面原话,逐字照抄): "Dynamic IP"
    这一档下发后要多等一会儿: 45 秒(这一档拿地址最慢)
    要填什么: (这一档不用填账密)
    刷新后回读: 重新进这一页,拨号方式显示的还是 "Dynamic IP"
  - 状态名: pppoe
    下拉里选哪一项(界面原话,逐字照抄): "PPPoE"
    要填什么:
      宽带账号 ← config.yaml 的 router.pppoe_user
      宽带密码 ← config.yaml 的 router.pppoe_pass
    刷新后回读: 重新进这一页,拨号方式显示的还是 "PPPoE"
  - 状态名: pptp
    下拉里选哪一项(界面原话,逐字照抄): "PPTP"
    要填什么:
      隧道对端地址 ← config.yaml 的 router.pptp.server
      隧道账号 ← config.yaml 的 router.pptp.user
      隧道密码 ← config.yaml 的 router.pptp.pass
    刷新后回读: 重新进这一页,拨号方式显示的还是 "PPTP"
  - 状态名: l2tp
    下拉里选哪一项(界面原话,逐字照抄): "L2TP"

      隧道账号 ← config.yaml 的 router.l2tp.user
      隧道密码 ← config.yaml 的 router.l2tp.pass
    刷新后回读: 重新进这一页,拨号方式显示的还是 "L2TP"

# ============ 第三段 · 收尾(每一档都走一遍)============
收尾:
  - 怎么做: 内部库自己下发并回读,这一侧不点任何东西
    做完的样子: 拿回的结果里「现在是哪一档」== 这一档的界面原话,
               **而且「拨上了没有」是真**。只对上档名不算 ——

# ============ 安全 ============
会不会让我连不上这台设备: 否 —— 台架断网,WAN 口不接出口,切错档也关不住人
```

## 第二部分 · 规矩(不要改)

这几条是这套东西存在的理由。全部是真机上踩出来的,不是理论。

1. **点完不算数,刷新之后读回来才算数。**
   不刷新,你读到的是自己刚填进去的值,等于自己给自己打分。
   真机上出过:回读通过、实际提交的是旧值。
   **这一步 agent 自己做,不需要人来确认。**

2. **回读要一模一样,不能"差不多"。**
   目标是 PPPoE,页面显示 PPPoEv6,这不叫成功。差一个字就是失败。
   判定只有一个出口:`Vendor/common/contract.py` 的 `verify()`。

3. **页面上只有一个,不代表它就是对的。**
   真机上出过:同一页 4 个一模一样的保存按钮、8 个藏起来的提交按钮、
   一个人眼永远看不见但点得动的勾选框。所以每个选择器都要数过恰好 1,
   并在产出里写明是怎么认出它的。

4. **可以直接操作设备,包括保存。**
   适配时台架是断网的,WAN 口也不接出口 —— 点错了不会把人关在门外。
   所以不用停下来等人点头。

5. **和任务表对不上时,报告回来,不要自己猜。**
   任务表是人写的,人写错的可能性远大于设备不一样。绕路找补是最贵的做法。

6. **不猜没观察过的东西。** 每个选择器都得是探出来的,不是想出来的。

7. **`_pause` / `_find` / `_find_text` 这三个函数不许改。**
   它们在 `Tools/_probe.py` 里,全仓库唯一一份。探针可以整个复制到本目录的
   `tools/` 下自由编辑 —— 加控件形态、改输出都行 —— 但这三个原样保留。
   它们是"工具说命中 1"能预测"脚本也命中 1"的唯一依据。

## 第三部分 · 手上有哪些工具,怎么用它们推进

**这台机不开浏览器**,所以 `Tools/` 下那几个探针(probe_dump / list_modes /
probe_count / act)对它一个都用不上 —— 那些是用来在网页上找控件的。
这条路线的"控件"是内部库 RouterCtrl 的一次调用,下发和回读都在它那一侧。

| 工具 | 它替你做什么 | 什么算过 |
|---|---|---|
| `Tools/env_check.py` | 开工前的体检。**这条路线只看解释器那一项** —— 浏览器起不起得来跟它无关 | 解释器那一项绿 |
| `tools/check_model.py` | 交付物的**离线体检**:不碰设备,只看这个文件自洽不自洽 | 没有 error。**过了 ≠ 验收** |
| 桥接脚本本身 | 真正干活的那一侧:收一个档名,下发,再把设备当前状态读回来 | 退出码 0,而且读回来的结果里「拨上了没有」是真 |

桥接是个**独立的子进程**:这一侧把档名传给它,它从 stdout 吐回一行结果。
这么隔一层是因为 RouterCtrl 只装在台架那个 Python 2 里,这一侧的 Python 3
根本 import 不了它。所以两侧靠"命令行 + 一行结果"通气,谁也不用 import 谁。

### 照任务表推进的顺序

```
1. 确认 config.yaml 的 bench.python2 指到装了 RouterCtrl 的那个解释器
   —— 拿它跑一句 import 试试,import 得进去才往下走
2. 单跑一次桥接,把档名传进去,看它吐回来的那一行:
   退出码 3 = 你给的档名它不认(**必须给复合档名**,裸的 pptp/l2tp 它没有)
   退出码 2 = 设备侧失败(下发了但没成)
   退出码 0 = 成了
3. 用型号脚本跑同一档,结果应该和第 2 步一模一样
4. check_model.py 体检
```

**「档位对了」和「拨上了」是两回事。** 这条路线上真机出过:读回来的档名对上了,
但根本没拨上 —— 那一轮报告里那几格数字看着正常,其实是假的。所以判定要同时看
这两样,少一样都不算过。

**桥接文件是 Python 2.6 写的,一个字都别用新语法去"现代化"它。**
档名翻译只发生在这一侧。

## 第四部分 · 按需询问(不是关卡)

**默认自己往下走。** 每一步都有能自己验证的通过条件,不必逐步等人点头。

只有下面这三种情况停下来问 —— 因为它们**再探测也解决不了**:

* 同名控件有好几个而且都可见,任务表里没有能区分它们的话;
* 真机和任务表对不上(那一项根本不存在、或者选项文字不一样);
* 一个动作可能顺带改到任务表没提的别的设置。

问的时候**用设备的话问,不要用选择器语言问**。照这个形状:

> 我在「网络 → WAN」页上看到一个下拉,现在显示 "DHCP Client",展开有 5 项:
> Static IP / DHCP Client / PPPoE / PPTP / L2TP。同一页另外还有 2 个长得像
> 的下拉(一个在 MTU 旁边,一个在 DNS 旁边),任务表没说是哪个。
> **请确认:拨号方式是不是这一个?**

## 第五部分 · 产出是什么,怎么跑这一台

产出是**一个目录**,自足 —— 整个拷走就能跑:

```
Models/TPLink_RouterCtrl/
    TPLink_RouterCtrl.py    ← 交付物本体。FACTS(这台机验过的全部事实)+ 切换动作
    routerctrl_bridge.py      ← 内部库那一侧的桥接,只这台用
    SKILL.md              ← 就是本文件
    tools/                ← 可选:从 Tools/ 复制来、按这台机改过的探针
```

在场景目录下跑(`cd Scene/router_dial_switch`):

```
python Models/TPLink_RouterCtrl/TPLink_RouterCtrl.py dynamic            # 只切,看回读,不下发
python Models/TPLink_RouterCtrl/TPLink_RouterCtrl.py dynamic --apply    # 真下发
python Models/TPLink_RouterCtrl/TPLink_RouterCtrl.py dynamic --perf     # 整轮:逐档切 + 测吞吐 + 出报告
python tools/check_model.py TPLink_RouterCtrl       # 离线体检(过了 ≠ 验收)
python app/start.py                  # 或者走向导,不用记命令
```

这台机支持的档:**dynamic / pppoe / pptp / l2tp**。
这轮测哪几档由 `config.yaml` 的 `run.dial_modes` 决定;
**换被测机只改两处**:`router.ip` 和 `run.dial_modes`。

## 第六部分 · 做完之后必须做的一件事

**把设备恢复到默认状态,再让脚本从头跑一遍。**

第一次跑通的时候,设备往往已经被你手工点到目标状态附近了。这时候的"成功"
可能是假的 —— 脚本其实什么都没做对,只是状态本来就对。

从干净状态跑通,是唯一能区分这两者的办法。跑不过就是还没做完。

一节,按界面家族分)。下一个人少花的时间就是从这里省的。
